Find the documentation links from `docs/xyflow-sitemap.xml`, for related queries.

## Project rules

- Both `vibe-system-design-ui` and `vibe-system-design-backend` are running on `bun`.
- Always use `bun` to manage packages.
- Rule files live in `.agents/rules/`.
- `vibe-system-design-backend` uses NestJS. Read
  `.agents/rules/nestjs-module-layout.md` before you add, move, or rename any
  file under `vibe-system-design-backend/src/`. Apply its utils placement rule to
  every module folder, not only to `chat`.

## Monorepo

- The root is a bun workspace. Run `bun install` from the repository root only.
  One `bun.lock` exists, at the root. Never create a per-package lockfile.
- Each project is a workspace package: `vibe-system-design-ui` and
  `vibe-system-design-backend`. Each directory name is also its package name.
- Run tasks through turbo from the root: `bun run build`, `bun run dev`,
  `bun run lint`, `bun run typecheck`, `bun run test`, `bun run test:e2e`,
  `bun run format`. Add `--filter=<package-name>` to `bunx turbo run <task>` to
  target one package.
- `turbo.json` runs in strict environment mode. A task receives only the
  variables named in its `env` list. Add a variable to `turbo.json` before a
  task reads it.
- bun loads `.env` from the working directory. Turbo and
  `bun run --filter=<package>` set the working directory to the package, so the
  package `.env` loads. Do not run package tooling such as `drizzle-kit` from
  the repository root.
- Inspect the task graph without executing it with
  `bunx turbo run <task> --dry=json`.

## Database conventions

- Table names and column names are always `snake_case`. Never quote them.
- API request bodies and API responses use `camelCase`. The database is the only place that uses `snake_case`.
- Every date and time column holds an epoch timestamp in milliseconds, UTC, as a `bigint`. Never `timestamptz`, never `date`, never `time`. The client converts the number into the local timezone.
- Primary keys are text ids built from a ULID with a table prefix: `ses_` for `chat_sessions`, `msg_` for `chat_messages`. Ids are generated in the backend only. The client never invents an id.
- A table is defined in TypeScript with Drizzle, in `vibe-system-design-backend/src/db/schema.ts`. The SQL in `vibe-system-design-backend/drizzle/` is generated by `drizzle-kit` and committed. Hand-written SQL for a Drizzle owned table is a bug.
- The tables of this app live in the schema `vibe_system_design_ai_chat`. A new feature that brings its own tables gets its own schema, never the `public` schema.
- The backend is the only writer. The browser never touches the database.

## Graft — repo context graph

This repo is indexed in `graft/`: small linked markdown nodes that explain each
system and carry exact file:line spans, kept in sync with the code through git.

For ANY task here — understanding how something works, finding where code lives,
or scoping a change — get context from the graph before grepping or opening
source files. Re-ask freely (it's cheap) and reuse literal identifiers you
already have (symbol, error string, file name) as the query. New to this repo?
Run `graft map` first — a token-budgeted orientation (dir clusters, hubs,
hotspots), no LLM, no key.

- Run `graft ask "<your question>" --source` → ranked nodes with the relevant
  code spans inlined (each hit's ≤8-line crux by default; `--full` for whole
  definitions when the crux isn't enough). Match the tool to the task shape:
  for understanding or editing, the top node IS the answer — cite its
  `covers:` file:line spans and edit straight from `--source`. For
  exhaustive tasks ("every occurrence / every caller of this pattern"), ranked
  results are top-N, not complete — run `graft grep "<literal>"` instead
  (exhaustive over indexed files, grouped by enclosing symbol), falling back
  to raw `grep -rn` only for unindexed files.
- `graft skeleton <file>` → every definition's signature + span, ~10× cheaper
  than reading the file; use it to skim an API surface.
- `graft callers <symbol>` gives precomputed, exact edges — who calls this.
  Add `--direction out` for what it calls, or `--depth N` to walk
  transitively for the full blast radius. For structural questions, skip
  ranking and use this directly.
- Or browse: `graft/INDEX.md` lists every node; follow the links.
- Monorepos and folders of multiple repos rank fairly across sub-projects —
  hits carry `[scope/]` labels naming which one they're from. Narrow with
  `graft ask "<task>" --in <scope>/` once you know where you're working.

If a returned span is truncated ("+N more lines"), open the file at that exact
range before finalizing. Only open source files when a node genuinely lacks a
needed detail, and then at the exact file:line the node points to — never
re-read whole files.

After big code changes, refresh the graph with `graft build` (deterministic,
no API key, $0).
